# Workflow 10 - interactive dashboard

Workflow 10 is the final presentation and output-cataloguing layer of the LivingEvidenceMap pipeline. It builds the public dashboard and also maintains an internal, repository-only registry of pipeline outputs.

## Locked production architecture

Workflow 10 is generated from the latest authoritative Workflow 08 final canonical state after successful Workflow 09 publication.

The accepted dashboard interface includes:

- headline evidence-map metrics;
- geography and country filtering;
- publication-year summaries;
- species-by-topic summaries;
- hierarchical topic navigation;
- model-agreement stars for topic assignments; and
- the interactive filtered bibliographic database table.

The production dashboard deliberately does **not** include the retired full-text search/download feature:

- no title/abstract search panel;
- no abstract inverted index;
- no reconstructed full abstracts;
- no RIS download generated by W10.

The public database table remains part of the accepted interface. It retains the normal bibliographic/table fields and a maximum 30-word abstract snippet. Full abstracts are not present in the public dashboard payload.

The preserved restoration reference is:

- `docs/dashboard-search-trial.html`
- `R/workflow_10_build_search_trial.R`
- `.github/workflows/workflow_10_search_trial.yml`

The search-trial workflow is manual-only so the retired search/RIS machinery cannot be regenerated accidentally.

## Authoritative inputs

W10 resolves the current authoritative Workflow 08 state from:

- `docs/workflow08/zenodo_registry.csv`
- the corresponding published Workflow 08 pointer; and
- the validated Workflow 09 publication handoff.

Record counts and canonical checksums are read dynamically from those authoritative inputs. W10 must not contain release-specific hard-coded counts or canonical SHA values.

## W09 to W10 handoff

Successful Workflow 09 completion writes:

`docs/reporting/.run_workflow10_dashboard`

with Workflow 09 provenance. W10 listens to that dedicated trigger file.

This avoids premature or duplicate W10 builds from intermediate Workflow 08/09 file commits while remaining branch-native before the workflow files are merged to the default branch.

W10 also updates the current-run Shiny status when dashboard generation starts and completes.

## Internal output registry

Each successful W10 run generates a repository-only output registry and archives it by the current search date under:

`internal/output_registry/archive/YYYY-MM-DD/`

Each dated archive contains:

- `output-registry.html` — a browsable internal catalogue;
- `output-registry.json` — the machine-readable registry;
- `output-registry-files.csv` — a flat file catalogue; and
- `manifest.json` — checksums for the registry files.

The registry records:

- database/search provenance and search dates;
- Workflow 00–08 Zenodo archive records;
- the actual Zenodo DOI as linked display text, without the `https://doi.org/` prefix;
- workflow stage, state, source run and publication date;
- reports, RIS exports, figures, validation summaries, codebooks and workflow metadata;
- W10 dashboard build outputs; and
- file sizes and SHA-256 checksums where applicable.

The registry is **not a public dashboard output** and is deliberately stored outside `docs/`. It is intended to remain with the pipeline repository and, once the repository is private, to remain private with it.

All workflow Zenodo deposits represented in this registry are expected to be **restricted**. W10 treats this as a validation invariant and fails registry generation if a workflow Zenodo record is not restricted. There is no separate public-release Zenodo record generated by W10.

## Deployment

While development remains on `workflow01-final-architecture`, validated W10 output can be previewed from `main` without replacing the production homepage by deploying it as:

- `docs/index2.html`
- deployment-only `index2-data.js`

The preview Pages bundle can also include the validated Workflow 09 `methodology.html` and `results.html`.

After final merge, production deployment can replace the temporary `index2.html` route only after the merged W09/W10 chain has been validated.

The internal output registry is excluded from this deployment path and is not copied into the public website bundle.
