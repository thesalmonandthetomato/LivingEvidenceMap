LivingEvidenceMap full-text coding PROMPT ADDENDUM — supersedes conflicting instructions in fulltext_coding_prompt_v1.txt

Apply this addendum after reading the base prompt. Where the base prompt conflicts with this addendum, this addendum controls.

1. PROVENANCE METADATA IS NOT PART OF THE COMPLETENESS AUDIT
DOI and year are supplied/maintained by the separate provenance database and must NOT be treated as substantive coding fields for field_completeness or not_reported_fields. Do not spend coding effort trying to recover them from the article. If present in the supplied record, preserve them; if absent, do not mark them NOT FOUND.

2. COMPLETENESS STATUS SEMANTICS — NO FOUND VALUE
The word/value "FOUND" is PROHIBITED everywhere in field_completeness. Never output FOUND for any field.

field_completeness is an exception/status audit, not a second copy of the extracted data:
- If a substantive field has a valid extracted value, OMIT that field from field_completeness. Its presence in the main record is sufficient evidence that it was found.
- If a substantive field applies to the document but the relevant information cannot be found after actively searching the appropriate full text, include it in field_completeness with exactly the string "NOT FOUND" and include the same field in not_reported_fields.
- If a substantive field is genuinely not applicable, include it in field_completeness with JSON null. Do not put it in not_reported_fields.
- Do not use "FOUND", "NOT_REPORTED", "NOT_APPLICABLE", true, false, empty strings, or any other status value inside field_completeness. The ONLY permitted field_completeness values are JSON null and the exact string "NOT FOUND".
- A populated main-record field MUST NOT simultaneously have a field_completeness status of "NOT FOUND" or null.
- A field omitted from field_completeness is interpreted as successfully found/populated.

field_completeness may contain ONLY substantive schema fields. It must NOT contain source_id, openalex_id, doi, title, year, schema_version, document_completeness_evidence, non_methods_results_evidence, non_methods_results_evidence_fields, not_reported_fields, field_completeness, evidence, run_metadata, or any other metadata/provenance field.

The substantive field universe is:
document_type, review_type, study_type, study_design, research_approach, setting, sample_size, sample_unit, study_period, location_region, location_country, species, other_farmed_species, study_population, aquaculture_facility, system_studied, production_stage, fish_life_stage, impact_type, impact_details, outcome_measured, exposure_intervention, comparator, methodology_for_data_collection, funding_body, funder, research_question, objectives_summary, ontology_codes, multiple_studies_flag, multiple_studies_reason.

Every substantive field therefore has exactly one logical state: (a) populated in the main record and OMITTED from field_completeness; (b) applicable but absent, represented by "NOT FOUND" and listed in not_reported_fields; or (c) genuinely inapplicable, represented by JSON null and absent from not_reported_fields.

3. DERIVE NOT_REPORTED CONSISTENTLY
not_reported_fields MUST contain exactly the substantive fields whose field_completeness value is "NOT FOUND". Do not independently invent or maintain this list. Do not put fields with null status in not_reported_fields. Do not put populated fields in not_reported_fields.

4. SCHEMA VALUE VS COMPLETENESS STATUS — DO NOT CONFUSE THEM
JSON null is permitted as a completeness status. It does NOT mean that every main-record field should itself be null.
- If the schema requires an enum value such as review_type, study_type, study_design or research_approach and the field is inapplicable, use that field's schema value "not_applicable".
- If the schema requires an array and there are no applicable values, use an empty array [].
- Use JSON null in the main record only where the schema defines the field as string|null or another nullable type.
- Use JSON null in field_completeness to indicate that the substantive field is genuinely inapplicable.
- Do not replace schema-valid "not_applicable" or [] values with null merely because the field is inapplicable.

5. PROVENANCE AND DOCUMENT STATUS
Do not use field_completeness for DOI/year or workflow provenance. document_completeness_evidence, non_methods_results_evidence, evidence, and run_metadata are outside the substantive completeness audit.

6. COMBINE INTERVENTION AND EXPOSURE
There is ONE combined substantive field: exposure_intervention.

Do NOT output separate intervention or exposure fields.

Use exposure_intervention for any deliberate intervention, assigned treatment, challenge, manipulation, environmental exposure, naturally occurring exposure, production-system exposure, dietary exposure, geographic exposure, host-associated exposure, or other exposure/intervention relevant to the eligible evidence.

The distinction between intervention and exposure is intentionally not required because the classification depends on the analytical lens and is often minor. Describe the relevant factor in neutral terms.

For a deliberate concentration gradient or drug-dose comparison, study_design = CI is defensible where the concentrations constitute the focal treatment/comparison conditions. Do not downgrade such studies merely because the intervention is a chemical exposure or bioassay concentration series.

For non-primary documents, exposure_intervention may contain explicit system-level exposure/intervention context. Do not inherit empirical methods or outcomes from cited studies merely because the document discusses them.

7. EVIDENCE FOR EVERY CODED FIELD — MANDATORY
Every substantive field that is populated with a value must have an evidence object or evidence entry that supports that specific coding. Evidence must come from the article/full text being coded and must include enough surrounding context to make the coding auditable. Do not use general knowledge, another paper, a citation to another source, or the model's own inference as the evidence itself.

Use the smallest contiguous passage that adequately supports the coding, rather than an unnecessarily long quotation. Where the coding is an inference explicitly permitted by these instructions, the evidence must still be the article text on which the inference is based, and the evidence should make clear that the coding is inferred rather than explicitly stated.

Do not require a Methods/Results passage for system/context variables in non-primary documents where this addendum explicitly permits those variables to come from any section. The evidence requirement applies regardless of document type.

8. FISH LIFE STAGE — BODY MASS AND METHODS-BASED INFERENCE
Life stage may be inferred from body mass, age, developmental descriptors, or production information ONLY when the supporting information appears in the Methods/Materials and Methods or an equivalent study-design section for the fish being coded. Do not infer life stage from the Introduction, Discussion, abstract, title, cited background literature, or general knowledge alone.

Use the following conservative operational guideline for salmon-specific coding:
- Atlantic salmon: body mass >= 1.0 kg may be coded as Adult when the fish are in a grow-out/production context or otherwise clearly beyond juvenile/smolt size and the article gives no contradictory life-stage designation.
- Atlantic salmon 0.5 to <1.0 kg is borderline: code Adult only when additional Methods context (e.g. adult grow-out, sea-cage grow-out, maturity or explicit adult terminology) supports it.
- Atlantic salmon <0.5 kg must NOT be coded Adult from mass alone.
- For other large-bodied salmon species where no species-specific threshold is established in the article, use the conservative >=1.0 kg Adult threshold only when the fish are clearly beyond juvenile/smolt production context; otherwise leave life stage NOT FOUND when applicable.

Never infer a specific earlier stage such as Smolt, Parr, Fry or Juvenile from body mass alone unless the Methods provide additional supporting context. Body mass can support Adult classification when sufficiently diagnostic; it does not replace explicit evidence where the mass is ambiguous.

If the Methods show that fish progress through more than one life stage during the study, code all life stages that are supported by the Methods rather than only the starting stage.

Example: an Atlantic salmon experiment using approximately 3 kg fish may be coded fish_life_stage = Adult even if the article does not explicitly use the word adult, provided the supporting mass/context appears in Methods.

Production stage and fish life stage remain independent variables. "Pre-market" is a production-stage/context descriptor, not itself a fish life-stage value. Pre-market fish may be coded Adult where body mass and/or other Methods evidence support Adult.

9. NON-PRIMARY SYSTEM/CONTEXT VARIABLES
Commentaries, perspectives, reviews, editorials, books, book chapters and reports may contribute the following system/context variables when explicitly described for eligible salmon/farmed-salmon content:
species; other_farmed_species; location_region; location_country; aquaculture_facility; system_studied; production_stage; fish_life_stage; setting; exposure_intervention.

These may come from any section of the document. Do not require Methods/Results for these context variables in non-primary documents.

A real-world production context may legitimately be coded setting = field. Do not force laboratory/controlled facility merely because the article mentions tanks, experimental facilities or controlled systems elsewhere. Choose the setting that actually characterises the eligible system/context being coded. If the document explicitly describes a field/open-cage production context and there is no basis for assigning laboratory/controlled facility as the relevant context, field is appropriate.

10. SPECIES IDENTIFICATION
If an eligible salmon species is explicitly named, ALWAYS use its specific permitted species value rather than "unspecified salmon species". In particular, Chinook salmon must be coded as "chinook salmon" whenever explicitly identified. Use "unspecified salmon species" only when the source establishes salmon but does not permit identification to one of the named controlled-vocabulary species.

11. PRODUCTION STAGE
Do not over-infer production_stage from generic aquaculture language. However, where the document explicitly describes a salmon production stage, code it. Production stage and life stage are independent.

12. EXPOSURE/INTERVENTION AUDIT
During the field-by-field audit, actively search for deliberate treatments, concentration gradients, challenges, dietary manipulations, environmental exposures, natural exposures, production-system exposures and other focal factors. A field should not be marked NOT FOUND merely because the factor was previously labelled intervention rather than exposure (or vice versa).

13. SAMPLE SIZE AND SAMPLE UNIT — SAME METHODOLOGICAL CONCEPT
sample_size and sample_unit MUST describe the same underlying methodological unit of analysis or sampling. Do not report a numerical sample size unless the corresponding sample unit is identifiable from the article.

Do not combine or conflate numbers referring to different entities, such as fish, cages, farms, sites, samples, replicates, simulations, scenarios, treatments, or observations. If a paper reports several different counts, select the count corresponding to the unit that is actually the study's sample/analytical unit, and identify that unit explicitly in sample_unit.

For modelling studies, distinguish modelled farms/sites, simulations, scenarios, or other model entities from an empirical sample size. Do not label a modelled quantity as sample_size unless the study design clearly treats those entities as the study units. The evidence supporting sample_size must also support the corresponding sample_unit.

14. MULTIPLE-STUDIES BOOKKEEPING
If multiple_studies_flag = false, multiple_studies_reason is genuinely inapplicable: set multiple_studies_reason = null and omit that field from field_completeness. If multiple_studies_flag = true, provide a concise reason in multiple_studies_reason and omit that field from field_completeness.

15. REVIEW TYPE BOOKKEEPING
For non-review documents, review_type must be the schema's not_applicable value and is genuinely inapplicable for completeness purposes: represent its field_completeness status as null if included. For reviews, provide the appropriate review_type value and omit review_type from field_completeness.

16. DOCUMENT COMPLETENESS — DO NOT CONFUSE EXTRACTION ARTEFACTS WITH INCOMPLETENESS
Do not declare the document incomplete merely because GROBID contains duplicated text, malformed references, OCR/extraction artefacts, repeated sections, broken formatting, or other local corruption. If the supplied text contains enough article structure and substantive content to identify and code the document, code it normally and record any relevant extraction limitation only in evidence where useful.

Return document_type = null and leave substantive coding blank ONLY when the supplied text is genuinely insufficient to identify/code the article as a whole — for example, a short fragment, severe truncation before substantive content, or an otherwise unusable extraction. In that case document_completeness_evidence is required. Do not use a local GROBID defect as a reason to discard otherwise usable article content.

17. VALIDATION BOUNDARY
There is no semantic validation prompt. The scientific coding prompt is authoritative for substantive decisions. Any automated checking, if used, must be limited to deterministic JSON/schema and bookkeeping constraints and must not decide whether a field should be reported or whether a scientific coding judgement is correct.

18. FINAL OUTPUT REQUIREMENT
Return exactly the schema-defined top-level fields. The combined field is exposure_intervention; intervention and exposure are prohibited legacy fields. field_completeness may contain ONLY substantive fields and ONLY the values null or "NOT FOUND". Found/populated substantive fields are omitted from field_completeness. not_reported_fields must exactly match the fields marked "NOT FOUND". The string/value FOUND is prohibited.
